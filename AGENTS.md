# AGENTS.md

Guidance for AI coding agents (Claude Code, and any complementary models/tools) working in this repository.

## What this is

A static, dependency-free PWA calculator (`Calculadora BCV · Binance P2P`) for Venezuela: standard arithmetic plus live conversion between USD and bolívares using the official BCV rate and the Binance P2P parallel rate. No framework, no bundler, no build step — see README.md for the product description and deployment notes.

## Commands

- **Run all tests:** `npm test` (alias for `node --test`)
- **Run a single test file:** `node --test test/calc.test.js` (or `test/rates.test.js`)
- **Run a single test by name:** `node --test --test-name-pattern="percent"` (matches the `test(...)` title)
- **Preview the app locally:** `python3 -m http.server 8000` from the repo root, then open `index.html` in a browser — there is no dev server or build step.
- **No lint/typecheck/build commands exist** in this repo — it's plain HTML/CSS/JS served as-is.
- **Push to `develop`:** every finished change is committed and pushed straight to `develop` (standing approval from the owner, no PR); the push auto-deploys. Use the `git-push-develop` skill (`.claude/skills/git-push-develop/SKILL.md`) for the exact steps.

## Architecture

- **`index.html`** contains the entire UI: markup, CSS, and the DOM/event-wiring JavaScript (keypad input, display rendering, currency conversion panel, rate rows, live-rate fetch, theme toggle, PWA install prompt, service worker registration). It intentionally has **no calculator logic of its own** — its inline `<script>` only calls into `calc.js`'s engine and re-renders based on the engine's state.
- **`calc.js`** is the pure, DOM-free calculator engine: tokenizing, `evalExpr` (precedence-aware parser for `+ − × ÷` and parens), number formatting (`groupNumber` — a no-op today, kept as the single seam for display formatting: no thousands separator, `.` is the only decimal point), rate parsing (`parseRate`, plain `.`-decimal with a `,`→`.` fallback for values saved before this format), and currency formatting (`fmtVES`/`fmtUSD`, `toFixed(2)`). It's wrapped UMD-style so the same file works as `window.CalcEngine` in the browser and via `require("../calc.js")` in Node — this is what `test/calc.test.js` exercises with Node's built-in test runner (`node:test`). **Any change to arithmetic/tokenizing/formatting behavior belongs in `calc.js`**, not duplicated inline in `index.html`.
- **Currency conversion mode**: a `mode` variable in `index.html` ("usd" or "ves") controls conversion direction — "usd" treats the typed amount as USD and shows Bs; "ves" treats it as Bs and shows USD. Default is `"ves"` (Bs → USD) per product decision. The mode toggle button label and the `mode` variable must stay in sync (`"Bs<br>⇄ USD"` ↔ `"ves"`, `"USD<br>⇄ Bs"` ↔ `"usd"`).
- **`rates.js`** is the pure, DOM-free rates logic (same UMD pattern, `window.Rates` / `require("../rates.js")`, tested by `test/rates.test.js`): parsing dolarapi responses, Caracas date (`caracasToday`, fixed UTC-4), `pickBcv` (splits the **published** BCV rate — the one bcv.org.ve shows, usually with a *future* fecha valor because the BCV publishes the next business day's rate each afternoon — from the **vigente** one, the last with fecha valor ≤ today), staleness check, and manual-override bookkeeping. **Any change to how rates are chosen, dated or overridden belongs in `rates.js`.**
- **Rate rows**: up to three — BCV publicada, BCV vigente, Binance P2P. When publicada and vigente are the same fecha valor (most of the day) only one BCV row is shown. Each row's title carries its fecha valor (`BCV · mar 24`); the hollow dot marks a published rate that doesn't apply yet. Because the cache keeps the last 15 BCV entries, the published rate becomes vigente on its date even offline.
- **Manual overrides are never overwritten by a refresh.** BCV overrides are keyed by fecha valor plus the published fecha at the time of the edit (`{pubFecha, values}`) and are dropped (with a notice) only when the BCV publishes a newer rate. The P2P override stays until the user taps ↺. Clearing the input or typing the official value also clears the override. `renderRow` never rewrites an input that has focus.
- **Rates persistence**: everything rate-related lives in one `localStorage` JSON under `rates.v2` (`bcv` entries, `p2p` auto reference, `fetchedAt`, `bcvOverride`, `p2pOverride`). v1.3's loose keys (`bcvRate`, `p2pRate`, `lastFetch`) are migrated once and removed. The theme stays under `theme`.
- **Live rate fetch**: `ve.dolarapi.com/v1/historicos/dolares/oficial` (BCV series with fecha valor, including the already-published next one) plus `/v1/dolares` (current oficial as fallback + the `paralelo` average). `/v1/dolares/oficial` alone is **not** enough: it only returns the vigente rate, which is why the app used to disagree with bcv.org.ve every afternoon. Binance P2P's API sends no CORS headers, so it can't be queried from the browser; the P2P row auto-fills with dolarapi's `paralelo` as a labelled reference (`ref. dolarapi`) and is meant to be adjusted by hand. Fetch happens on open, on the Actualizar button, when coming back online, and when the app becomes visible (at most once a minute).
- **`sw.js`** is a cache-first service worker for offline PWA use. Its `SHELL` array must list every file the app shell needs (including `calc.js` and `rates.js`), and `CACHE` must be bumped (e.g. `calc-bs-v6` → `v7`) whenever any shelled file changes, or offline clients won't pick up the update.
- **App version**: `APP_VERSION` in `index.html`'s inline script (mirrored in `package.json`'s `version`) is shown in the footnote (`v1.4.0`) so users can visually tell a new version was deployed. Bump it — together with the `sw.js` `CACHE` key — on every user-visible change.
- **Update banner**: `sw.js` already calls `skipWaiting()`/`clients.claim()` on install, so a new SW takes over an already-open tab automatically — the tab just doesn't know until it reloads. `index.html` tracks whether the page already had a controller before registering (`hadController`), and a later `controllerchange` event (a *second* controller taking over, not the first) reveals the `#updateBadge` link in the footnote ("Nueva versión, toca para actualizar"), which just does `location.reload()`. It also forces `registration.update()` on `visibilitychange` and every 5 minutes, since browsers otherwise only check for a new `sw.js` sporadically. This is what replaces manually clearing the cache after a deploy.
- **Deployment**: `.github/workflows/deploy-pages.yml` deploys the raw repo contents (no build step) to GitHub Pages on every push to `develop` (Pages source: GitHub Actions; custom domain `calc.ubbedigital.com` set in Settings → Pages).
- **Git workflow**: commit + push directly to `develop` after every finished change, no confirmation needed; conventions in `.claude/skills/git-push-develop/`.
- UI copy and code comments are in Spanish; keep new user-facing strings consistent with that. Numbers themselves are locale-agnostic (see App version / `calc.js` note above): plain `.` decimal point, no thousands separator anywhere in the UI.
